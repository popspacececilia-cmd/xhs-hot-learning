# 沉淀、交接和规则生命周期

## 目录

1. 标准保存包
2. 账号工作区交接
3. 候选规则
4. 内容机会
5. 状态回写
6. 反馈演化

## 标准保存包

每篇保存：

- 原始来源和采集结果。
- 事实底稿、缺失项和置信度。
- 核心机制及其证据和推断。
- 可迁移、不可迁移和账号适配。
- 原创迁移建议。
- 候选规则和内容机会。
- 处理台账及可追踪样本 ID。
- 人工可读 Markdown 视图，说明抓到了什么、分析出了什么、证据强弱、能否迁移、内容机会和缺失项。

## 账号工作区交接

通用 skill 不保存账号私有偏好。把标准保存包写入用户指定的个人运营 skill 项目工作区，由后者结合账号定位、语言、人设、阶段和历史反馈继续生产内容。

同一素材优先使用收件箱、采集记录、分析记录和候选规则的结构化模型。没有兼容模型时保存为清晰的 Markdown/JSON，并说明字段映射。

项目中的标准样本包使用稳定 `sample_id`，并按以下目录保存：

```text
00_样本清单.md
01_原始来源/
02_素材底稿/
03_机制分析/
04_账号迁移/
05_候选规则/
06_内容机会/
07_处理记录/
```

机器 JSON 继续保存在 `.xhs-personal-content-skill/real-sample/` 作为底账；项目目录下的 Markdown 是用户主阅读入口。采集记录、分析、候选规则、规则证据、内容机会和个人运营记录均保留同一个 `sample_id`。

人工可读单篇目录建议：

```text
01_原始来源/
├── 链接与采集信息.md
├── 灵造原始返回说明.md
├── 完整逐字稿.md
└── 高赞评论.md
02_素材底稿/
├── 文字层.md
├── 图片层.md
├── 视频层.md
└── 数据评论层.md
03_机制分析/
├── 标题-封面-开头承接.md
├── 用户任务与评论需求.md
├── 核心机制.md
└── 证据强弱与替代解释.md
04_账号迁移/
├── 可迁移性与制作成本.md
└── 原创迁移建议.md
05_候选规则/
└── 候选规则证据.md
06_内容机会/
└── 内容机会与标题方向.md
07_处理记录/
└── 完成状态与缺失项.md
```

候选规则的证据必须说明来源类型、事实位置、推断、置信度、证据强度和替代解释；内容机会必须回链来源样本和候选机制。

## 候选规则

单篇规则只设为 `candidate`，每篇最多 3-5 条。每条包含：

- 名称、来源和可见事实。
- 推断、置信度和替代解释。
- 证据强度：强 / 中 / 弱 / 不可判断。
- 适用与不适用场景。
- 风险和账号迁移方式。
- 需要的对照样本。

优先更新同类规则的证据，不创建重复规则。不自动批准、测试、验证、拒绝、废弃或删除。

## 内容机会

每篇最多给出 3 个方向，包括目标问题、核心判断、借鉴机制、实质区别、原创增量、热点/长期价值、内容形式、制作成本、所需证据、风险和待验证策略。

每个内容机会还必须写明：

- 学到的规则或候选机制。
- 为什么这样起标题。
- 数据依据。
- 评论依据，尤其是多次出现的需求。
- 原创增量。
- 证据强度和不确定项。

不要自动生成完整草稿或发布任务，除非用户明确要求。

## 状态回写

完成采集、底稿、机制、账号迁移、候选规则/内容机会、工作区写入和校验后，使用 `scripts/inbox_status.py mark` 将唯一命中记录的 `状态` 值改为 `已处理`。

只修改状态行，不改链接、顺序、收藏原因、备注或其他字段。写入失败时不声称完成。

## 反馈演化

规则生命周期：

```text
单篇观察 -> candidate -> 多样本重复 -> 用户确认 -> testing
-> validated / revised / rejected / deprecated
```

发布前记录本次验证目标、采用/未采用规则、人工修改和制作成本。发布后记录指标、真实评论、账号适配、修改成本和用户主观判断。一次成功不永久固化，一次失败不自动删除。

规则升级需要多次证据支持：单篇强证据只能进入 candidate evidence；多篇样本重复出现、边界清楚、用户确认适合当前账号并经过发布验证后，才能成为当前账号有效规则。

规则淘汰同样要记录：如果一个规则多次没有得到印证，或反例持续出现，应从可用规则清单移出，转为 rejected、deprecated 或 needs_revision，并保留证据和原因。
